# معماری هدف: پلتفرم مستقل مدیریت و آموزش انگلیسی

وضعیت: طرح پیشنهادی برای اجرا؛ جداسازی فیزیکی و استقرار در این مرحله انجام نشده است.
تاریخ: ۲۰۲۶-۱۰-۰۷
محدوده: مدیریت آموزش، نه مدیریت یا نظارت بر گوشی.

## ۱. تصمیم اصلی

دو محصول مستقل با یک بک‌اند آموزشی مشترک:

```text
مدیر/مربی → پنل وب مستقل → احراز هویت + مجوزهای سمت سرور
                                      ↓
                     بک‌اند آموزشی / پایگاه‌داده / Storage
                                      ↑
زبان‌آموز → اپ مستقل اندروید → احراز هویت + مجوزهای سمت سرور
```

- پنل در مبدا وب جدا منتشر می‌شود؛ اپ APK و چرخه انتشار مستقل دارد.
- ورود و نشست هر محصول مستقل است. نقش حساب را سرور تعیین می‌کند، نه مسیر URL یا متغیر داخل اپ.
- تغییر پنل نباید مستلزم ساخت APK جدید باشد.
- انتشار محتوای استاندارد جدید از طریق سرور ممکن می‌شود؛ افزودن نوع تمرین یا قابلیت جدید ممکن است همچنان نیاز به APK جدید داشته باشد.
- استفاده از یک مخزن چندبرنامه‌ای (monorepo) به معنی یک محصول مشترک نیست؛ خروجی‌ها و استقرارها جدا هستند.

## ۲. وضعیت فعلی و فاصله با هدف

- اپ فعلی Expo/React Native است؛ پنل نسخه اول در app/admin/index.tsx در همان پروژه قرار دارد.
- نشست پنل از نشست زبان‌آموز جدا شده، ولی هنوز bundle، مسیریابی و انتشار مستقل نیستند.
- lib/educationAdmin.ts ورود مدیر، داده نمایشی و دریافت گزارش را پوشش می‌دهد.
- app/learning-access.tsx عضویت آموزشیِ رضایت‌محور را پیاده می‌کند.
- migration مربوط به education_admins/invites/enrollments و آزمون RLS محلی موجود است؛ نصب آن روی سرور واقعی از این بررسی قابل تأیید نیست.
- محتوای ۱۲۹ درس و ۵۰۴ واژه در کد اپ قرار دارد. پنل فعلی فقط فهرست آن را می‌خواند.
- پیشرفت محلی با learning_progress همگام می‌شود؛ هنوز مدل کامل چنددستگاهی، دفتر رخداد معتبر و مهاجرت حساب مهمان وجود ندارد.
- کد و سیاست‌های قدیمی دستگاه در مخزن باقی مانده‌اند. برای محصول آموزشی جدید نباید به ارث برده شوند.

## ۳. ساختار پیشنهادی مخزن

```text
apps/
  learner/                  # Expo / React Native؛ اندروید و پیش‌نمایش وب
  admin/                    # React + TypeScript + Vite؛ پنل وب فارسی
packages/
  contracts/                # قراردادهای API، مدل‌ها و اعتبارسنجی مشترک
  curriculum/               # محتوای اولیه معتبر و ابزار import/export
  learning-engine/          # منطق خالص مرور، بدون وابستگی به UI/سرور
  design-tokens/            # رنگ و تایپوگرافی؛ نه اجبار به UI یکسان وب و native
backend/
  supabase/
    migrations/
    functions/              # عملیات مدیریتی، AI، همگام‌سازی و انتشار
    tests/                  # آزمون نقش‌ها و جداسازی سازمان‌ها
scripts/
docs/
```

تکنولوژی پیشنهادی پنل: Vite/React Router، TanStack Query برای داده سرور، React Hook Form و Zod برای فرم/اعتبارسنجی. انتخاب Vite به‌جای یک سرور اضافی برای پنل خصوصیِ بدون نیاز SEO است. اگر بعداً نشست cookie-based با BFF لازم شد، آن را به‌صورت تصمیم مستقل اضافه می‌کنیم.

محدودیت import: پنل حق import از apps/learner ندارد و برعکس. اشتراک فقط از packages عمومی است. هیچ secret یا SDK دارای service_role وارد این packages نمی‌شود. اجزای UI وب و اندروید جدا هستند.

## ۴. ماژول‌های پنل همه‌کاره آموزشی

| ماژول | قابلیت هدف | اولویت |
|---|---|---|
| هویت و دسترسی | ورود مدیر، MFA، نقش‌ها، نشست‌ها، بازیابی حساب | پایه انتشار |
| کاربران | دعوت، عضویت، جستجو، گروه، وضعیت دسترسی، درخواست حذف داده | مرحله اول |
| دوره و محتوا | سطح، درس، جمله، واژه، گفتگو، ترتیب و پیش‌نمایش | مرحله دوم |
| انتشار محتوا | پیش‌نویس، اعتبارسنجی، نسخه منتشرشده، بایگانی و بازگشت نسخه | مرحله دوم |
| برنامه آموزشی | تخصیص دوره/درس به گروه، هدف و مهلت | مرحله سوم |
| گزارش | پیشرفت همگام‌شده، مرور، تکمیل تکلیف و خروجی مجاز | مرحله سوم |
| اطلاع‌رسانی | اعلان داخل اپ، هدف‌گیری گروه، زمان‌بندی؛ push پس از راه‌اندازی | مرحله سوم |
| هوش مصنوعی | روشن/خاموش، سهمیه و سقف مصرف، خطاها و هزینه تخمینی | مرحله چهارم |
| عملیات | سابقه تغییرات، سلامت سرویس، پشتیبان‌گیری و تمرین بازیابی | از پایه و توسعه تدریجی |
| پرداخت و اشتراک | فقط در صورت نیاز تجاری و انتخاب درگاه | اختیاری، خارج از شروع |

«همه‌کاره» یعنی پوشش چرخه مدیریت آموزش. به معنی دسترسی نامحدود به پیام خصوصی یا دستگاه، اجرای دلخواه SQL از پنل، یا دسترسی مستقیم مدیر به secretها نیست.

## ۵. نقش‌ها و مرز اعتماد

- owner: صاحب آموزشگاه؛ مدیریت مدیران، تنظیمات حساس و مشاهده حسابرسی.
- admin: مدیریت کاربران، گروه‌ها و محتوای آموزشگاه؛ بدون ارتقای خود به owner.
- teacher: فقط گروه‌ها و زبان‌آموزان تخصیص‌یافته؛ بدون کلیدها، نقش‌دهی یا گزارش سایر گروه‌ها.
- learner: فقط حساب، عضویت، تکلیف و پیشرفت خودش.

شروع محصول یک آموزشگاه و یک owner است؛ organization_id از ابتدا در جداول وابسته وجود دارد تا توسعه بعدی به بازنویسی جداسازی داده نیاز نداشته باشد. جدول نقش کاربر و نقش سازمانی قابل نوشتن توسط خودِ کاربر نیست. اولین owner از مسیر مورداعتماد سرور/داشبورد ایجاد می‌شود.

RLS روی تمام جداول قابل دسترسی فعال می‌شود. عملیات حساس از RPC/Edge Function با احراز هویت، بررسی نقش، محدوده سازمان، اعتبارسنجی ورودی و audit انجام می‌شود. اگر service_role در یک تابع استفاده شد، همان تابع باید تمام بررسی‌های مجوز را انجام دهد؛ service_role خود RLS را دور می‌زند.

نشست مدیر: مبدا مستقل، MFA برای مدیران، خروج واقعی، بازاحراز هویت برای تغییر نقش و تنظیمات حساس، جلوگیری از ثبت token در log. راه‌اندازی CSP و عدم رندر HTML واردشده بدون پالایش. MFA باید در سرور با سطح نشست مناسب بررسی شود، نه صرفاً نمایش فرم.

## ۶. مدل داده هدف

```text
organizations
organization_members       (org_id, user_id, role, status)
learner_profiles            (user_id, display_name)
groups / group_members / teacher_groups
invites                    (org_id, token_hash, intended_email?, expiry, claimed_at)
consents                   (org_id, learner_id, version, granted_at, revoked_at)
courses / course_versions
lessons / lesson_versions / sentences / vocabulary / dialogues
content_releases           (course_version_id, manifest_hash, min_app_version, status)
enrollments                (learner_id, course_id, access_status, valid_until)
assignments / assignment_targets / assignment_results
learning_events            (event_id, learner_id, course_version, server_received_at)
progress_snapshots / review_state
announcements / announcement_targets
ai_policies / ai_usage
admin_audit_log
```

organization_members با enrollment در دوره و consent اشتراک گزارش یک مفهوم نیست. «تعلیق دسترسی آنلاین» از «لغو رضایت گزارش» جدا نگه داشته می‌شود. خروج رضایت نباید به‌طور ضمنی داده آموزشی فرد را پاک کند.

دعوت‌ها: token تصادفی قوی، ذخیره hash در مدل هدف، یک‌بارمصرف، انقضا، محدودیت نرخ، پذیرش تراکنشی با قفل ردیف. در صورت تعیین ایمیل مقصد، ایمیل تأییدشده باید تطبیق داشته باشد. نام مدیر/آموزشگاه و موارد اشتراک قبل از پذیرش نمایش داده می‌شود. UUID دعوت نسخه اول مرحله میانی است و باید مهاجرت سازگار داشته باشد.

## ۷. قراردادهای API هدف

نام‌ها مفهومی‌اند؛ پیاده‌سازی می‌تواند RPC یا Edge Function باشد.

- GET /me: هویت و نقش‌های تأییدشده، بدون دریافت نقش از ورودی کلاینت.
- POST /admin/invites، POST /invites/preview، POST /invites/accept.
- GET /admin/learners با صفحه‌بندی، فیلتر و محدوده مجاز.
- POST /admin/enrollments/:id/suspend و resume با علت و audit.
- POST /admin/content/import: دریافت ساختار معتبر، بررسی و پیش‌نمایش؛ نه انتشار خودکار.
- POST /admin/releases/:id/publish: تراکنش انتشار نسخه تأییدشده.
- GET /learner/content-manifest: نسخه قابل دریافت برای این کاربر.
- POST /learner/progress/sync: رویدادهای شناسه‌دار و پاسخ canonical سرور.
- POST /admin/assignments و /admin/announcements.
- POST /ai/chat: کنترل دسترسی و سقف مصرف در سرور؛ کلید AI فقط در secret store.

الگوی پاسخ خطا: code پایدار + پیام قابل نمایش + requestId غیرحساس. مثال: ACCESS_SUSPENDED، INVITE_EXPIRED، AI_QUOTA_EXHAUSTED. هیچ خطای داخلی SQL، token یا پاسخ خام ارائه‌دهنده نباید به کاربر نهایی نشت کند.

## ۸. مدیریت و انتشار محتوا

۱. curriculum موجود به‌عنوان نسخه اولیه با شناسه‌ها و ترتیب فعلی وارد شود.
۲. import ابتدا اعتبارسنجی ساختار، یکتایی ID، روابط، تعداد اولیه و پوشش ۵۰۴ را انجام دهد.
۳. تغییرات به‌صورت draft ذخیره شوند؛ مدیر پیش‌نمایش ببیند.
۴. انتشار یک نسخه immutable بسازد. کلاینت manifest و سازگاری min_app_version را بررسی کند.
۵. نسخه جدید به‌صورت اتمیک cache شود؛ دریافت ناقص نباید جای نسخه سالم را بگیرد.
۶. نسخه قبلی برای rollback و تفسیر پیشرفت کاربران حفظ شود.

نباید درس تکمیل‌شده کاربر با تغییر متن یا شناسه، بی‌صدا معنای دیگری بگیرد. مدل پیشرفت باید course_version را نگه دارد. شمارش ۱۲۹/۷۷۱/۵۰۴ معیار نسخه اولیه است؛ انتشار بعدی می‌تواند بزرگ‌تر باشد ولی با تغییر صریح انتظار آزمون.

## ۹. آفلاین، پیشرفت و هویت

- درس‌ها و مرور باید بدون شبکه اجرا شوند.
- رویدادها ابتدا محلی ذخیره و با event_id یکتا به سرور ارسال شوند؛ retry نباید دوباره امتیاز بدهد.
- سرور user_id را از نشست می‌گیرد، نه ورودی JSON. snapshot مشتق‌شده باید قابل بازسازی باشد.
- زمان دستگاه برای گزارش رسمی قابل اعتماد نیست؛ server_received_at و محدودیت ورودی جدا ثبت می‌شوند.
- برای تعارض مرور چنددستگاهی، نسخه وضعیت و سیاست تعارض مستند لازم است؛ صرف upsert کل JSON کافی نیست.
- حالت مهمان حفظ‌پذیر است، ولی عضویت مدیریتی پایدار به حساب قابل بازیابی نیاز دارد. تبدیل مهمان به حساب باید همان هویت را حفظ کند یا مهاجرت تأییدشده داشته باشد.
- تغییر حساب نباید پیشرفت محلی کاربر قبلی را برای کاربر جدید upload کند. storage باید account-scoped باشد و مهاجرت اطلاعات قدیمی با تأیید انجام شود.

## ۱۰. معنی واقعی محدودکردن دسترسی

مدیر می‌تواند ورود به خدمات آنلاین، دریافت محتوا و APIهای آموزشی را مطابق enrollment متوقف کند. پیش‌فرض پیشنهادی: درس دانلودشده برای استفاده آفلاین باقی بماند و تعلیق فقط خدمات آنلاین را ببندد.

اگر دوره با مدت اعتبار لازم شد، signed entitlement با مهلت آفلاین مشخص طراحی می‌شود؛ مثلاً مهلت قابل تنظیم چندروزه. این سازوکار DRM قطعی نیست و محتوای قبلاً دانلودشده یا APK قابل کپی را نمی‌توان از راه دور تضمینی حذف کرد. هیچ پاک‌سازی گوشی یا کنترل دستگاه در معماری آموزشی نیست.

## ۱۱. AI و هزینه

- کلید خصوصی داخل اپ، bundle پنل یا EXPO_PUBLIC قرار نمی‌گیرد.
- سهمیه اتمیک در سرور برای کاربر/آموزشگاه و سقف سراسری تعریف شود.
- کاربر نباید مقدار سقف را در درخواست تعیین کند؛ تابع فعلی consume_daily_ai_usage با p_limit ورودی برای مدل هدف باید بازطراحی و دسترسی مستقیم به آن محدود شود.
- زمان رزرو/مصرف/بازگشت سهمیه برای خطاها روشن باشد؛ درخواست شکست‌خورده نباید بی‌قاعده هزینه یا سهمیه ثبت کند.
- هزینه تخمینی از usage واقعی ارائه‌دهنده و قیمت ثبت‌شده محاسبه شود، نه تعداد پیام به‌تنهایی.
- پنل وضعیت کافی‌بودن اعتبار را با خطای شبکه اشتباه نگیرد.

## ۱۲. مهاجرت بدون خراب‌شدن نسخه فعلی

فاز A — جداسازی بسته‌ها:
- ثبت baseline و اجرای آزمون‌های موجود.
- ساخت apps/admin و انتقال رابط پنل از Expo به وب مستقل؛ نشست و خروجی مستقل.
- انتقال اپ به apps/learner همراه حفظ alias، assetها، lockfile و scripts ساخت.
- انتقال منطق خالص و قراردادها به packages و تست عدم وابستگی متقابل.
- حذف مسیر و کد پنل از bundle زبان‌آموز پس از تأیید جایگزین؛ مسیر قدیمی می‌تواند موقتاً صفحه راهنما باشد، نه پنل کامل.

فاز B — بک‌اند آموزشی امن:
- پیشنهاد استفاده از پروژه Supabase جدا برای محیط عملیاتی آموزشی، چون پروژه فعلی جداول و policyهای قدیمی دستگاه دارد.
- مدل نقش/سازمان، RLS، دعوت، consent، audit و حساب قابل بازیابی آماده شود.
- داده واقعی فقط با برنامه انتقال/پشتیبان‌گیری و تأیید منتقل شود؛ هیچ SQL حذف گسترده اجرا نشود.
- پیش از توزیع APK آموزشی، onboarding دستگاه، مجوزهای کنترل/اشتراک صفحه، سرویس accessibility و runtime دستگاه از خروجی آموزشی کنار گذاشته شوند؛ کد قدیمی در Git محفوظ می‌ماند.

فاز C — کاربران و گزارش:
- فهرست واقعی صفحه‌بندی‌شده، گروه‌ها، وضعیت دسترسی، همگام‌سازی و گزارش معتبر.
- آزمون حداقل دو مدیر و دو زبان‌آموز و تلاش دسترسی متقاطع.

فاز D — CMS و انتشار:
- import نسخه اولیه، ویرایش draft، انتشار، cache آفلاین و rollback.

فاز E — تکلیف، اعلان و AI:
- تکلیف، گزارش، اعلان داخل اپ و سپس push؛ سیاست هزینه AI و پایش.

هر فاز خروجی قابل نمایش و آزمون پذیرش مستقل دارد. فایل export قدیمی صرفاً snapshot محتواست و با تغییر پنل/اپ خودکار به‌روز نمی‌شود.

## ۱۳. استقرار و عملیات

- development، staging و production تنظیمات و داده جدا داشته باشند.
- پنل روی دامنه HTTPS مستقل، اپ از کانال انتشار APK/AAB مستقل، بک‌اند در Supabase آموزشی مستقل.
- CI برای پنل: typecheck، unit، build، آزمون مرورگر و انتشار پنل.
- CI برای اپ: typecheck، منطق محتوا/مرور، تست همگام‌سازی و build اندروید با امضای امن.
- migration با بازبینی و نسخه‌بندی؛ rollback برنامه/محتوا از rollback پایگاه‌داده تفکیک شود.
- لاگ با حذف داده حساس، شناسه درخواست، alert خطای سرویس، سیاست retention و تمرین restore پشتیبان.
- audit فقط از سرور ثبت شود؛ نقش مدیر معمولی اجازه حذف سابقه خود را نداشته باشد.
- هزینه میزبانی/ساخت/پیامک/ایمیل/AI ممکن است وجود داشته باشد؛ رایگان‌بودن همیشگی تضمین نمی‌شود.

## ۱۴. معیار پذیرش نهایی جداسازی

- admin و learner جدا نصب وابستگی/اجرا/build شوند و انتشار یکی دیگری را تغییر ندهد.
- bundle اپ هیچ صفحه مدیریتی، secret یا ابزار کنترل دستگاه نداشته باشد.
- ثبت‌نام عادی نتواند نقش مدیر بسازد؛ تغییر URL یا JSON نتواند محدودیت نقش را دور بزند.
- مدیر فقط افراد/گروه‌های مجاز را ببیند. با لغو رضایت، دسترسی آینده به گزارش قطع شود.
- کاربر حساب دوم نتواند پیشرفت محلی حساب اول را دریافت یا upload کند.
- محتوای اولیه دقیقاً با مرجع فعلی تطبیق داشته باشد؛ پیشرفت قبلی گم نشود.
- قطع شبکه، دریافت ناقص محتوا، همگام‌سازی تکراری و rollback آزمون شوند.
- نتیجه آزمایش واقعی روی گوشی اندروید و مرورگر ثبت شود؛ صرف موفقیت unit test به معنی آماده انتشار نیست.

## تصمیم پیشنهادی برای شروع

یک مخزن چندبرنامه‌ای، دو خروجی مستقل، پنل وب Vite/React و اپ Expo، بک‌اند آموزشی مستقل برای production. نخست فقط فاز A اجرا شود؛ تا وقتی استقلال build و حفظ رفتار آموزشی تأیید نشده، CMS و ماژول‌های بزرگ دیگر به پروژه اضافه نشوند.
